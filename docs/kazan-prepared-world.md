# Prepared world pipeline

Run `aube run prepare-world` to regenerate prepared assets, or `aube run build` to prepare them and build the release. CI runs the same build command. The source geography remains the mapped input; generated assets in `public/compiled-world/` are ignored by Git.

`tools/build-kazan-world.mjs` installs the source geography and runs explicit subsystem recipes. The input hash includes geography, JavaScript, compiler recipes, codec and dependency versions. An unchanged input skips generation. The release version also hashes generated descriptors and content, so platform/compressor differences cannot reuse an immutable manifest URL. Each asset has a content hash; the manifest is written atomically and gets a release-specific filename. The browser verifies the map/release versions. Content-addressed files use immutable HTTP caching. Obsolete local outputs move to `.cache/compiled-world/` instead of entering the release.

The current recipes are:

- `compile-kazan-terrain.mjs`: prepare the existing terrain levels, exact shore cuts and underground openings. Preserve their position, normal, UV and index values. Fetch distant exact detail when the existing 6.5 km terrain LOD needs it; keep coarse terrain present until detail is ready.
- `compile-kazan-roads.mjs`: project mapped roads onto the terrain offline and partition the resulting triangles into 1 km regions without changing corner values or material/deck families. Load detailed streets near the camera and prefetch ahead. Keep elevated decks and stairs present citywide. Evict distant road owners and geometry while retaining browser HTTP caching.
- `compile-kazan-markings.mjs`: prepare the existing lane/crosswalk/stop-bar geometry from the actual drivable graph and structural clearances, preserving every shader attribute and dash phase. Share road-region loading, prefetch and eviction. The runtime checks static clearance signatures and regenerates markings if a future obstacle-producing feature has not yet been included in the compiler recipe. Extend `compile-kazan-traffic-inputs.mjs` when adding that kind of feature.
- `compile-kazan-traffic.mjs`: prepare exact live junction/lane/turn tables in Float64 and Uint32 buffers. Restore the mapped road references and create actor state/clearance queries at runtime. Validate the obstacle signature before use; fall back to live construction when a new obstacle system has not entered the recipe. The current global asset adds5.73MB compressed and releases its transport buffers after restoring live records. Regional graph streaming is a separate trade-off.
- `compile-kazan-ground.mjs`: paint the existing landcover/park/ground atlas offline and include the actual distant road paths/widths. It supplies geographic context beyond the detailed road region without citywide road triangles.

Geometry uses lossless Meshopt encoding and gzip transport. Ground atlases use lossless WebP; their decoded pixels match the PNG output. The decoder writes typed data into one allocation; it does not rebuild polygons, triangulate banks, compute normals or expand vertices into JavaScript objects. Shader/material families and dynamic simulation remain runtime systems. Ambient traffic omits the physical-paint snapshot; clearance recovery constructs the complete physical graph independently, preserving dead-end streets. Map teleports wait for destination terrain/roads; a stale earlier request cannot override a later arrival.

For another subsystem, add a `compile-kazan-<system>.mjs` recipe and register it in the compiler list. Reuse `writeGeometry` for procedural mesh families and `writeImage` for painted atlases, then consume its manifest entries through `loadPreparedWorld`. Additional static tables can get their own typed-data writer/reader when required. Boats, for example, can prepare shared hull meshes, water masks and route tables offline while keeping motion, steering and animation at runtime. Do not bake a whole set of moving actors or eagerly download all regions.

Before publishing changes, run the relevant native geometry/transport and lifecycle checks, the test suite, and the release build. Inspect screenshots through camera movement and a distant map round trip; measure startup and actual Aerial renders with tracing stopped. The existence of prepared assets alone proves neither the loading nor the FPS target.

Rail/power follow-ups use the same tradeoff: prepare regional beds and static surfaces; store poles, supports and repeated parts as shared geometry plus typed instance fields. Keep tram actors and their transforms dynamic. Check transfer size, resident geometry and actual render cost before adopting a representation; preparing every world-space part eagerly can enlarge the download without improving FPS.

The geography compiler exports `GEO_DATA_VERSION` in `js/kazan-geodata.js`. Both the download cache key and prepared-map consistency check use this generated payload hash. A running development server therefore follows regenerated maps through its usual module reload, without depending on a hash fixed at server startup. Release-specific world manifests still enforce release/map consistency.

The published rail/tram recipe adds shared repeated-unit instance assets. Exact Float32 transforms and linear colours are packed by region/material family, Meshopt/gzip encoded and decoded into shared storage views. Bridges/portals stay present, local beds use the same3.5/5.5/9km residency policy as ground roads, and sleepers/catenary retain their original512m owners and1.2/1.8km visibility/eviction radii. Distant reserved track corridors are painted into the ground atlas; street-embedded rails do not paint over road pavement. Map destinations await both network regions. Live paths, platforms, vehicles, signals and collisions remain separate. `createInstanceCompiler` and `prepareRegionalInstances` are reusable for future static unit-part systems; power-line matrices and conductors are not migrated yet. The rail/tram checkpoint passed native full-part equivalence and browser movement/map-return checks; its latest integrated Aerial sample was31.52FPS. Future recipes still require their own rendering/loading/FPS evidence.
